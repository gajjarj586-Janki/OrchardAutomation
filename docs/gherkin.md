# Gherkin generation & validation

`npm run generate:features` turns each `requirements/*.md` file into `features/<same-basename>.feature` via the configured `AIProvider.generateFeature()`. The AI response is untrusted output and goes through:

1. **Schema validation** - `GeneratedFeatureSchema` (Zod) checks the response has a non-empty `title` and `content`.
2. **Content/syntax validation** - `validateFeatureFile()` parses the Gherkin with `@cucumber/gherkin` (real syntax validation, not a hand-rolled regex parser) and additionally requires: a Feature, at least one Scenario, every scenario named and non-empty, and no lines that look like an embedded secret (password/API key/token/AWS key patterns).

If validation fails, `AIClient.withValidation()` retries the whole generation up to `ai.maxRetries` times (default 3), then throws rather than writing invalid output.

Generation is idempotent: the feature file is only rewritten if its content actually changed (`npm run generate:features` reports `CREATED` / `UPDATED` / `UNCHANGED`).

## `npm run validate:features`

Re-validates every `features/*.feature` file already on disk (useful after a manual edit, or in CI before running tests) and exits non-zero if any file fails.

## The mock AI provider

The only `AIProvider` implemented in framework core is `MockAIProvider` (`src/ai/providers/MockAIProvider.ts`) - fully deterministic, offline, and every `.feature` file it produces is stamped `# Generated by MOCK AI provider - for framework verification only.` It exists to prove the pipeline mechanics, not to write meaningful test coverage. See [ai.md](./ai.md) for how to add a real provider.
